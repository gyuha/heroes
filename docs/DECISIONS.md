# DECISIONS

주요 설계 결정을 기록한다. 결정을 바꿀 때는 기존 항목을 지우지 않고, 새 항목에 변경 이유와 영향을 적는다.

## D-001 기술 스택: TypeScript + three.js (2026-10-23)

- **결정:** 게임은 TypeScript로 작성하고 렌더링은 three.js를 쓴다.
- **이유:** 사용자의 명시적 요구사항이다.
- **영향:** 엔진 에디터 없이 코드로 씬을 구성한다. 빌드 도구와 모듈 구조는 테크니컬 아키텍트가 `docs/ARCHITECTURE.md`에 정한다.

## D-002 레퍼런스 게임은 분석만 하고, 코드와 리소스는 직접 만든다 (2026-10-23)

- **결정:** 레퍼런스 게임(https://hank1105.itch.io/heroes-battlefield-demo)은 REA로 분석해 게임 규칙, 시스템 구조, 연출 방식을 파악하는 데만 쓴다. 그 게임의 코드, 이미지, 사운드, 데이터는 우리 저장소에 복사하지 않는다. 우리 게임의 코드와 리소스는 팀이 직접 만든다.
- **이유:** 사용자의 목표는 "이런 게임처럼" 대규모 군대가 싸우는 전략 게임을 만드는 것이다. 다른 사람의 저작물을 그대로 옮기면 저작권 문제가 생기고, 출시할 수 있는 게임이 되지 않는다.
- **영향:** 분석 결과는 `docs/REFERENCE_ANALYSIS.md`에 "관찰한 사실"과 "우리 게임에 쓸 시사점"으로 나눠 적는다. 기획은 이 문서를 참고해 `docs/GDD.md`에 우리 설계로 다시 정리한다.

## D-003 지형과 캐릭터는 3D로 만들고, 지형이 전략에 영향을 준다 (2026-10-23)

- **결정:** 지형(높낮이, 경사, 지형 종류)과 병사 캐릭터를 모두 3D로 구현한다. 지형은 보기 좋은 배경이 아니라 이동 속도, 시야, 전투 결과에 영향을 주는 전략 요소로 설계한다.
- **이유:** 사용자의 명시적 요구사항이다.
- **영향:** 대량의 병사를 한 화면에 그려야 하므로 병사 모델은 인스턴싱(InstancedMesh)이 가능한 저폴리곤 형태여야 한다. 아트 디렉터와 테크니컬 아키텍트가 폴리곤 수와 리소스 형식을 함께 정한다.

## D-004 레퍼런스에서는 규칙·지휘 구조·UX를 가져오고, 렌더링은 따르지 않는다 (2026-10-23)

- **결정:** T-002 분석 결과 레퍼런스(Song of Ashes 데모)는 자체 WebGL2 2D 픽셀 스프라이트 게임이다. 우리는 `docs/REFERENCE_ANALYSIS.md` §11.1의 구조(상태 기반 상성, 수백 명 단위 부대, 전선·부관 구조, 다양한 승리 조건, 패주로 승부, 연속 줌 → 전술 지도)를 참고하고, §11.2처럼 3D 지형 효과를 눈으로 읽을 수 있게 만드는 것을 차별점으로 삼는다. §11.3의 무쌍 모드, 실존 역사 전투·인물, 판타지 마법 무기는 넣지 않는다.
- **이유:** 사용자의 목표는 "대량의 군사가 지형과 전략으로 싸우는 게임"이다. 수천 명을 쓸어버리는 영웅은 지휘와 지형의 가치를 지운다. 2D 렌더링 방식은 D-003(3D)과 맞지 않는다.
- **영향:** GDD(T-004)는 지휘 중심으로 설계한다. 지휘관은 전장에 있는 유닛이지만 전투력은 보조 수준으로 둔다. 1차 목표(MVP)는 전투 맵 1개, 2진영, 병종 4종(보병·창병·궁수·기병), 지형 종류(평지·경사/고지·숲·강과 다리·절벽), 동시 시뮬레이션 5,000~10,000명이다. 병사 수 상한은 테크니컬 아키텍트와 QA의 측정 결과로 확정한다.

## D-005 레퍼런스 스크린샷은 분석 근거로만 쓰고 git에 올리지 않는다 (2026-10-23)

- **결정:** `docs/reference/*.jpg`는 로컬 분석 근거로 두고, 저장소 커밋에서는 제외한다(`.gitignore`).
- **이유:** D-002에 따라 레퍼런스 게임의 이미지를 우리 저장소에 넣지 않는다. 분석 문서의 결론은 텍스트로 충분히 남아 있다.
- **영향:** `.gitignore`는 테크니컬 아키텍트 담당 파일이므로, T-003 작업이 끝난 뒤 게임 디렉터가 한 줄을 추가한다.

## D-006 빌드 스택과 규칙·렌더 분리 (2026-10-23)

- **결정:** Vite 8 + pnpm 10 + TypeScript 7(strict) + three.js 0.186. 게임 규칙(`src/sim`)은 three.js와 브라우저 API를 import하지 않고, 렌더(`src/render`)와 분리한다. 시뮬레이션은 초당 20틱 고정이고, 렌더는 두 틱 사이를 보간한다. 유닛 데이터는 구조체 배열(SoA)과 2m 균일 격자를 쓴다. 상세는 `docs/ARCHITECTURE.md` §1~§6.
- **이유:** 규칙을 엔진 없이 테스트하고, 수천 명 규모에서 GC 부담을 줄이며, 나중에 Web Worker로 옮길 수 있게 하기 위해서다.
- **영향:** 분리 규칙은 `pnpm typecheck`(별도 tsconfig)가 강제한다. 게임플레이 프로그래머와 UI·UX 디자이너는 이 경계를 지킨다.

## D-007 리소스 계약 (2026-10-23)

- **결정:** `docs/ARCHITECTURE.md` §7을 아트 리소스 계약으로 삼는다. `.glb` 단일 메시·단일 머티리얼, 보병 300삼각형/20본, 기병 700삼각형/40본, 256² 팔레트 텍스처의 알파 채널을 팀 색 마스크로 사용, 1=1m·+Y 위·+Z 정면·발 원점, 런타임 경로 `public/assets/`.

## D-008 성능 목표 (2026-10-23)

- **결정:** 내장 GPU 노트북(Apple M1 / Intel Iris Xe급, 1080p)에서 병사 5,000명 60fps, 확장 목표 10,000명.
- **이유:** 레퍼런스는 2D로 2만 명 안팎을 그리지만, 3D 병사는 정점 비용이 크다. 개발 기기 측정(시뮬레이션 1틱 2만 명 약 4ms)으로 여유가 확인되면 상향한다.
- **영향:** QA(T-011)가 목표 기기급에서 측정해 확정한다.

## D-009 GDD 미결 쟁점 결정 (2026-10-23)

`docs/GDD.md` §12의 쟁점 5건을 디자이너 권장대로 결정한다.

- **MVP 시나리오는 비대칭 공방전**(맵 "갈대 여울", 방어 3,600 vs 공격 5,960, 깃발 60초 점령 / 15분 방어 / 상대 붕괴). 이유: "지형을 읽고 버티는" 재미를 가장 빨리 전달하고, 시뮬레이션(S6·S7)에서 지형 효과가 결과를 확실히 바꿨다. 병력비 1.66배는 가설이며, 구현 후 AI 대 AI 러너로 방어 승률 45~55%를 확인한다(BALANCE §7).
- **부대 단위 전장의 안개를 MVP에 넣는다**(GDD §6.4). 이유: 숲 은폐와 능선 뒤 예비대가 없으면 지형 전략의 절반이 사라진다. AI도 같은 시야 규칙을 따른다.
- **선택이 없으면 명령을 무시한다**(GDD §7.1). 백틱으로 전군 선택. 이유: 배치 위치 하나가 승패를 가르는 게임에서 실수로 전군이 움직이는 것을 막는다.
- **지형 종류 ID를 GDD §6.1대로 바꾼다.** 4 = 깊은 물(통과 불가), 5 = `ford` 여울, 6 = `bridge` 다리. 절벽 경사 기준은 30°로 통일한다. `docs/ARCHITECTURE.md` §7.6과 코드를 함께 고친다.
- **세계관·진영 이름은 가제로 둔다**(청람·황토). 출시 전에 다시 정한다.
- **전선·부관 위임은 MVP에서 뺀다**(GDD §7.3). 레퍼런스와 다르지만, 한 진영 15~25개 부대는 직접 지휘할 수 있고, 적 AI 검증이 먼저다.

## D-010 MVP 구현 작업 분할과 git 규칙 (2026-10-23)

- **결정:** 구현을 T-006(지형·맵·시야), T-007(부대·전투·사기·명령·AI·유닛 렌더), T-008(카메라·입력·HUD·오버레이)로 나눠 병렬로 진행한다. 파일 소유 범위는 `docs/TASKS.md`에 적는다. `src/main.ts`와 `src/app/`의 조립은 T-007 담당자가 맡고, 다른 담당자는 진입 함수만 제공한다. 병렬 작업 중 팀원은 git 커밋을 하지 않는다(같은 작업 트리에서 동시 커밋 충돌 방지). 커밋은 게임 디렉터가 마일스톤마다 한다.
- **이유:** 같은 작업 트리를 여러 에이전트가 동시에 쓰므로 파일 단위 소유가 충돌을 막는 유일한 장치다.
- **영향:** 소유 범위 밖 파일을 바꿔야 하면 그 파일의 담당자에게 ask_bot으로 요청한다.

## D-011 명령·조회 인터페이스 단일화와 구현 중 설계 확인 (2026-10-23)

- **결정 1 — 인터페이스 단일화:** 명령 타입은 B의 `src/sim/api.ts` `Command` 하나만 쓴다. UI 읽기 포트는 B의 `GameSession` 하나로 합치고, UI의 `UiGameView` 요구 목록(INTERFACES §3.3)은 `GameSession`에 들어갈 요구사항으로 바꾼다. UI 목업은 `GameSession`을 구현하는 형태로 만든다. 드래그 선분을 부대별로 나누는 일은 sim 순수 함수 하나가 맡고, UI 미리보기와 명령 적용이 같은 함수를 부른다. 큐는 `World.enqueue`, 검증은 sim 순수 함수(`validateCommand`)를 UI와 AI가 같이 쓰고, 적용 시점에 다시 판정한다.
- **이유:** 같은 일을 하는 타입과 어댑터가 두 벌이면 이름(`type`/`kind`, `skirmish`/`loose`)과 동작(선분 분할 위치)이 어긋나고, 변환 계층에서 버그가 생긴다. 규칙은 sim에 있어야 AI와 플레이어가 같은 규칙을 따른다(D-006).
- **결정 2 — `tsconfig.json`에 `allowImportingTsExtensions: true` 추가:** B의 `src/sim/rules.test.ts`가 디자이너 검증본 `tools/balance/rules.ts`와 결과를 대조하는데, 그 파일이 `.ts` 확장자 import를 써서 typecheck와 build가 실패한다. `noEmit` 설정이라 부작용이 없다. 테크니컬 아키텍트가 고친다.
- **결정 3 — 지형 설계 확인(게임플레이 프로그래머 A의 질문, 기본값 채택):**
  - 숲 LOS: 시선의 양 끝점에서 40m 안의 숲 칸은 장애물에서 뺀다. 숲 가장자리 40m 안의 부대는 밖을 보고 쏠 수 있고, 더 깊이 있는 부대는 못 본다. 숲 은폐 거리(40m)와 같은 값이라 규칙이 대칭이다.
  - 서쪽 벼랑: z 380~560 구간에서 x 40(맵 경계)~180 전체를 통과 불가로 막는다. GDD 원안(x 120~180)대로면 경계 안쪽 80m로 능선을 우회할 수 있어 "측면 고정" 의도가 깨진다.
  - 검은숲 "높이 10~14m": 지면 높이 10~14m의 완만한 기복으로 해석하고, 나무 모델 높이도 10~14m로 맞춘다.
- **영향:** UI·UX는 `UiCommand`·`UiGameView` 어댑터를 걷어내고 B의 타입을 쓴다. B는 §3.3 요구 목록을 `GameSession`에 넣는다. 게임 디자이너는 GDD §6.4·§10.2를 결정 3에 맞춰 고친다.

## D-012 월드 좌표의 동서 방향과 고저 가독성 기준 (2026-10-23)

- **결정 1 — 월드 +x는 서쪽이다.** three.js 좌표계(+y 위)에서 +x = 동, +z = 북으로 두면 북쪽을 위로 본 화면에서 동쪽이 왼쪽에 와서 지도가 좌우 반전된다. 코드와 맵 데이터는 그대로 두고, 문서와 화면 표기의 동서 이름을 바꾼다. 즉 **+x = 서, +z = 북**으로 정의한다. 북쪽이 위인 화면에서 동쪽이 오른쪽에 오고, 미니맵·전술 지도·나침반이 실제 화면과 일치한다.
- **이유:** z 방향을 뒤집으면(선택지 ②) 맵 생성기, 맵 파일 행 순서, 배치 구역, B·UI의 좌표가 모두 바뀌어 진행 중인 병렬 작업이 흔들린다. 가상의 맵이라 동서 이름만 바꾸면 게임플레이는 같다.
- **영향:** 게임 디자이너가 GDD §10(지형 배치 표, 요소 이름, 개략도)의 동·서 표기를 뒤집는다. 좌표 숫자는 그대로다. 예를 들어 지금의 "검은숲(동쪽, x 680~880)"은 "검은숲(서쪽)", "서쪽 벼랑(x 40~180)"은 "동쪽 벼랑"이 된다. 맵 데이터와 UI에 들어가는 지형 요소 이름도 같은 규칙을 따른다.
- **결정 2 — 고저 가독성을 지형 렌더의 완료 조건으로 삼는다.** 지형이 전략인 게임에서 능선이 평지처럼 보이면 핵심 재미가 전달되지 않는다. 전술 지도 거리와 기본 전투 카메라 거리 모두에서 매봉 능선의 마루선과 앞 경사, 북쪽 둔덕이 스크린샷만 보고 식별되어야 한다. 숲과 벼랑의 경계는 사각형이 아니라 자연스러운 외곽선이어야 한다(규칙 판정은 종류 맵을 따르므로 생성기에서 경계를 함께 바꾼다).

## D-013 이벤트 로그에 적 부대 정보를 어디까지 보여 줄지 (2026-10-23)

- **결정:** 플레이어의 이벤트 로그에는 아군 부대의 이벤트를 모두 보여 준다. 적 부대의 이벤트는 그 부대가 지금 플레이어에게 보이고(시야, GDD §6.4) 큰 사건일 때만 보여 준다. 큰 사건은 패주, 괴멸, 지휘관 전사, 깃발 상태 변화, 아군 부대에 대한 돌격 명중이다. 적의 "사거리 밖", "돌격 실패", "고지에서 싸우는 중" 같은 내부 판정 로그는 보여 주지 않는다.
- **이유:** 적의 내부 판정 로그는 안개로 숨긴 정보를 새게 하고(D-009), 같은 순간 여러 줄이 쏟아져 아군 로그를 밀어낸다. 로그의 목적은 "왜 이겼고 졌는지를 지형과 결정으로 이해하는 것"(GDD §6.5)이고, 그 대상은 플레이어 자신의 부대다.
- **영향:** UI·UX 디자이너가 로그 필터를 구현한다. AI 대 AI 관전 모드(`?aivai`)는 필터 없이 모두 보여 줘도 된다.

## D-014 MVP 균형 문제는 진단을 먼저 한다 (2026-10-23)

- **결정:** AI 대 AI에서 방어 승률이 100%(12/12, 모두 15분 시간 승리)다. 목표는 45~55%다. 병력비를 바로 고치지 않고, 게임 디자이너가 헤드리스 러너로 먼저 원인을 가른다. 원인이 공격 AI가 교전을 피하는 것이면 AI를 고치고(게임플레이 프로그래머 B), 교전은 충분한데 지는 것이면 수치를 고친다(디자이너).
- **이유:** 15분 동안 공격군 5,960명 중 약 4,100명이 살아 있고 패주는 수백 명이다. 공격군이 제대로 부딪치지 않았을 가능성이 높다. 이 상태에서 수치를 고치면 AI 결함을 수치로 덮게 된다.

## D-015 병사 장비 좌우 수정 방식 (2026-10-23)

- **문제:** 정면이 +Z인 캐릭터에서 +X쪽은 해부학적 왼쪽인데, 골격이 +X쪽 본에 `_r` 접미사를 붙였다. 그 결과 모든 보병 계열이 검·창을 왼손에, 방패를 오른손에 든다. 웨이트와 공격 동작은 서로 맞게 되어 있어서 장비만 옮기면 공격이 빈손을 휘두른다.
- **결정:** 본 이름·계층·바인드 변환은 바꾸지 않는다(`animations.glb`·렌더러 베이크·ARCHITECTURE §7.5와의 계약 유지). 장비를 해부학적으로 올바른 손(-X쪽, 이름은 `_l`)으로 옮기고 웨이트를 바꾼다(아트 디렉터). 공격 클립은 팔·손 트랙의 좌우 대상을 바꾸고 반사 부호를 맞춰 다시 생성한다(애니메이션·VFX). `_l`/`_r` 접미사가 해부학적 좌우와 반대라는 점은 ART_STYLE_GUIDE와 ANIMATION_GUIDE에 명시한다.
- **이유:** 각자 자기 파일만 고쳐 소유 범위(D-010)를 지키고, 본 이름을 바꿀 때 생기는 렌더러·문서 연쇄 수정을 피한다. 본 이름은 화면에 보이지 않으므로 문서화로 충분하다.
- **영향:** 두 작업이 끝나면 애니메이션 담당이 원본 골격 + `animations.glb` 재수입·재생 검사로 공격 프레임에서 무기가 오른손에 있는지 확인한다. 기병의 창도 같은 기준으로 확인한다.

## D-016 성능 대응 순서 (2026-10-24)

- **결정:** 아래 순서로 진행하고, 각 단계의 측정 결과를 보고 다음 단계를 정한다.
  1. **CPU 가비지 제거(B, A):** 시뮬레이션이 틱마다 약 1.3MB를 할당해 최악 틱이 137~390ms까지 튄다(아키텍트 T-012 2차 리뷰). 기준은 ARCHITECTURE §11.6 규칙 11(틱당 할당 100KB 이하, 최악 틱 20ms 이하).
  2. **UI 프레임당 낭비 제거(UI):** 경로선 정점 버퍼 1.7MB를 매 프레임 GPU에 다시 올림, 매 프레임 DOM 생성, 부대별 경로 미리보기 제한.
  3. **GPU 부하 대비(아트 → B):** 병사 삼각형이 약 272만 개다. 게임 디렉터가 Paseo 브라우저에서 잰 결과 CPU는 프레임당 12~17ms인데 프레임 전체는 88~140ms였다(GPU 병목인지 웹뷰 제한인지 미확정). 내장 GPU 목표(D-008)를 고려해 원거리용 보병 LOD1(ARCHITECTURE §7.3, 삼각형 80 이하, 같은 골격)을 미리 만들고, 렌더러 적용 여부는 일반 브라우저 실측 뒤 정한다.
  4. **측정(QA):** ARCHITECTURE §9.3 절차(`?scale=k`)로 다시 잰다.
  5. **Web Worker 이전:** 1~4 뒤에도 기준 기기에서 평균 틱이 8ms를 넘으면 그때 결정한다. 그 전까지는 한 틱이 4ms를 넘는 기기에서 4배속을 자동으로 막는다.
- **이유:** 할당 제거는 비용이 작고 효과가 확실하다(Math.hypot 교체만으로 가비지 32% 감소, 아키텍트 실험). Worker는 메인 스레드 멈춤은 없애지만 시뮬레이션 자체를 빠르게 하지 않으므로 마지막 수단이다.

## D-017 단건 지형 함수의 Math.hypot 교체와 LOD1 적용 (2026-10-24)

- **결정 1:** 단건 `moveFactor`/`moveFactorInto`와 경로 탐색 비용 계산에 남은 `Math.hypot`도 `Math.sqrt(x*x+z*z)`로 바꾼다(D-016 정정 범위). 일괄 함수 `moveFactorsInto`와 단건 함수가 정확히 같은 값을 내야 같은 병사를 어느 경로로 계산해도 결과가 같다.
- **결정 2:** 병사 렌더러에 원거리 LOD1(T-021)을 적용한다. 카메라에서 약 150m 밖의 병사는 LOD1로 그린다. 비교 측정을 위해 `?lod=0`으로 끌 수 있게 한다.
- **이유:** 1080p 150m에서 LOD0과 LOD1이 구분되지 않음을 디렉터가 확인했다(시각 손실 없음). 삼각형이 66~71% 줄고, Paseo 브라우저 측정에서 GPU 병목이 의심된다. 일반 브라우저 실측을 기다리지 않아도 손해가 없는 변경이다.
- **영향:** 이 두 변경은 시뮬레이션 결과의 마지막 비트를 바꾼다(결정 1). 균형 진단(T-015)의 결론은 AI 행동에 대한 정성 판단이므로 유지하고, 최종 승률은 AI 수정 뒤 새 코드로 다시 잰다.

## D-018 공개 GitHub 저장소와 제외 대상 (2026-10-24)

- **결정:** 사용자 요청에 따라 저장소를 GitHub 공개 저장소 `gyuha/heroes`로 올린다. 다음은 공개 저장소에서 뺀다(`.gitignore`, 로컬 파일은 그대로 유지).
  - `docs/REFERENCE_ANALYSIS.md`: 레퍼런스 게임의 능력치표를 그대로 옮긴 데이터(§3.1)와 역분석 세부(§1)가 들어 있다. D-002·D-005와 같은 이유로 공개하지 않는다.
  - `tools/art/*_poses.json`: 아트 검증 중간 데이터(합계 약 45MB). 생성 스크립트로 다시 만들 수 있다.
- **이유:** 우리 게임의 코드와 수치는 팀이 새로 만들었으므로 공개해도 된다. 상용 데모의 데이터와 역분석 세부를 공개하면 제작사의 삭제 요청이나 약관 문제를 부를 수 있다.
- **영향:** 다른 문서의 `docs/REFERENCE_ANALYSIS.md` 링크는 공개 저장소에서 열리지 않는다. 팀 작업은 로컬 사본을 계속 쓴다. 팀원은 앞으로도 커밋하지 않고(D-010), 게임 디렉터가 사용자 확인을 받아 커밋·push한다.

## D-019 GitHub Pages 배포 (2026-10-24)

- **결정:** 사용자 요청에 따라 게임을 GitHub Pages(`https://gyuha.github.io/heroes/`)에 배포한다. `main`에 push하면 GitHub Actions가 `pnpm test`를 통과한 경우에만 `pnpm build:pages`(Vite `--base=/heroes/`)로 빌드해 배포한다.
- **이유:** 런타임 리소스 경로가 이미 `import.meta.env.BASE_URL` 기준이라 기준 경로만 바꾸면 된다. 로컬에서 `/heroes/` 하위 경로로 띄워 28개 요청이 모두 200임을 확인했다. 테스트를 배포 조건으로 두어 깨진 빌드가 공개되지 않게 한다.
- **영향:** 런타임에 리소스를 불러오는 코드는 앞으로도 `/assets/...` 같은 절대 경로를 쓰지 말고 `import.meta.env.BASE_URL`을 붙인다. `main`에 push하는 것이 곧 공개 배포다(게임 디렉터가 사용자 확인 후 push).
